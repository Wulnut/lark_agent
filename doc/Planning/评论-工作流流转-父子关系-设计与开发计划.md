# 评论 / 工作流流转 / 父子关系能力：设计与开发计划

> 本文档用于固化本仓库在「飞书项目 (Lark Project)」Open API 之上补齐的三类通用能力：
> 1) 工作项评论 CRUD
> 2) 工作流运行时流转（含必填信息查询）
> 3) 关系驱动的父子/子任务操作
>
> 说明：本文档聚焦“能力与接口契约”，实现细节以 `src/` 与 `tests/` 为准。

---

## 1. 分层设计

本仓库沿用 Provider 模式，分层职责如下：

- **API 层（Data Layer）**：只做 HTTP 调用 + err_code 检查，不做业务编排。
  - 目录：`src/providers/lark_project/api/`
- **Provider 层（Service Layer）**：业务编排、参数解析、可读化输出、中文错误语义转换。
  - 目录：`src/providers/lark_project/`
- **MCP 层（Interface Layer）**：tool 注册、参数编排、统一错误处理。
  - 文件：`src/mcp_server.py`

---

## 2. 评论能力（Comment）

### 2.1 Open API 端点

- 创建评论：`POST /open_api/{project_key}/work_item/{work_item_type_key}/{work_item_id}/comment/create`
- 获取评论列表：`GET /open_api/{project_key}/work_item/{work_item_type_key}/{work_item_id}/comments`（query: `page_num/page_size`）
- 更新评论：`PUT /open_api/{project_key}/work_item/{work_item_type_key}/{work_item_id}/comment/{comment_id}`
- 删除评论：`DELETE /open_api/{project_key}/work_item/{work_item_type_key}/{work_item_id}/comment/{comment_id}`

### 2.2 API 层

- `src/providers/lark_project/api/comment.py`
  - `CommentAPI.create()`
  - `CommentAPI.list()`
  - `CommentAPI.update()`
  - `CommentAPI.delete()`

### 2.3 Provider 层

- `src/providers/lark_project/comment_provider.py`
  - 解析 `project_name/project_key` + `work_item_type_name`（通过 `MetadataManager`）
  - 输出精简结构（节省 token）：
    - add：`{"comment_id": ...}`
    - list：`{"total","page_num","page_size","items":[{"comment_id","author","create_time","content"}]}`
  - 捕获底层异常并转换为中文可读错误

### 2.4 MCP tools

- `add_task_comment(issue_id, content, project=None, work_item_type=None, user_key=None)`
- `list_task_comments(issue_id, page_num=1, page_size=20, project=None, work_item_type=None, user_key=None)`
- `update_task_comment(issue_id, comment_id, content, project=None, work_item_type=None, user_key=None)`
- `delete_task_comment(issue_id, comment_id, project=None, work_item_type=None, user_key=None)`

## 3. 工作流运行时能力（Workflow Runtime）

### 3.1 Open API 端点

- 查询工作项工作流信息：`POST /open_api/{project_key}/work_item/{work_item_type_key}/{work_item_id}/workflow/query`
- 获取流转前必填信息：`POST /open_api/work_item/transition_required_info/get`
- 执行状态流转：`POST /open_api/{project_key}/workflow/{work_item_type_key}/{work_item_id}/node/state_change`

### 3.2 API 层

- `src/providers/lark_project/api/workflow.py`
  - `WorkflowAPI.query_work_item_workflow()`
  - `WorkflowAPI.get_transition_required_info()`
  - `WorkflowAPI.state_change()`

### 3.3 Provider 层

- `src/providers/lark_project/workflow_provider.py`
  - `target_status`（人类可读状态名） -> `state_key/transition_id` 解析
  - `get_transition_requirements()`：返回最小结构 `{"required_fields": [...]}`
  - `transition_task_status()`：执行流转，当前最小实现 `fields: list[dict]` 透传
  - 捕获底层异常并转换为中文可读错误

### 3.4 MCP tools

- `get_task_transition_requirements(issue_id, target_status, project=None, work_item_type=None, mode="", user_key=None)`
- `transition_task_status(issue_id, target_status, fields=None, project=None, work_item_type=None, mode="", user_key=None)`

## 4. 父子/子任务能力（Hierarchy via Relation）

### 4.1 Open API 端点

- 获取关联规则：`POST /open_api/{project_key}/relation/rules`
- 获取关联工作项列表：`POST /open_api/{project_key}/relation/{work_item_type_key}/{work_item_id}/work_item_list`
- 批量绑定关联：`POST /open_api/{project_key}/relation/{work_item_type_key}/{work_item_id}/batch_bind`
- 删除关联：`DELETE /open_api/{project_key}/relation/{work_item_type_key}/{work_item_id}`

### 4.2 API 层

- `src/providers/lark_project/api/relation.py`
  - `RelationAPI.rules()`
  - `RelationAPI.work_item_list()`
  - `RelationAPI.batch_bind()`
  - `RelationAPI.delete()`

### 4.3 Provider 层

- `src/providers/lark_project/hierarchy_provider.py`
  - 关联规则选择策略：
    - `relation_name` 传入：按名称精确匹配
    - 未传：rules==1 自动选；rules>1 要求指定并列出候选
  - `list_child_tasks()`：当前最小输出 `work_item_ids: list[int]`
  - `bind_child_tasks()`：绑定后返回 `{"parent_issue_id","child_issue_ids","relation_name"}`
  - `unbind_child_tasks()`：解绑后返回 `{"parent_issue_id","relation_name"}`
  - 捕获底层异常并转换为中文可读错误

### 4.4 MCP tools

- `list_child_tasks(parent_issue_id, relation_name=None, page_num=1, page_size=20, project=None, work_item_type=None, user_key=None)`
- `bind_child_tasks(parent_issue_id, child_issue_ids, relation_name=None, project=None, work_item_type=None, user_key=None)`
- `unbind_child_tasks(parent_issue_id, relation_name=None, project=None, work_item_type=None, user_key=None)`

## 5. 测试策略

- API 层：每个方法至少 `success + err_code` case；断言 path 与 payload/params。
- Provider 层：覆盖核心编排（状态/规则选择）与中文错误转换。
- MCP 层：patch Provider，断言 project_name / project_key 分支与 JSON envelope 结构。

对应测试目录：
- `tests/unit/providers/lark_project/api/`
- `tests/unit/providers/lark_project/`
- `tests/unit/`
